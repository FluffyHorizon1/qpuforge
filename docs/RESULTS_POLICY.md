# Policy for committed results, designs and GDSII assets

Scope: everything tracked under `results/`, `designs/` and `docs/` that a program or a script produced: review JSON and
text, CSV, calibration caches, generated specs, GDSII masks, and SVG/PNG renderings of them. The machine-readable half of this
policy is `tools/results_policy.json`; the checks are `tools/check_reproducibility.py` and `.github/workflows/reproducibility.yml`.
Status: **proposed** (backlog item q15). Section 6 lists the decisions that still need the owner's yes.

## 1. What belongs on `main`

| class | examples | rule |
|---|---|---|
| **A. Review numbers** (JSON, text, CSV) | `designs/*/*_review.{json,txt}`, `results/design_study.*` | Commit. Small (tens of kB). Generated by code only, never edited. |
| **B. Derived specs** | `designs/beta1/BETA-1.md`, `designs/gamma1/GAMMA-1.md` | Commit. A pure function of a review JSON and its `.template.md` (`tools/fill_spec.py`); the check regenerates them. |
| **C. GDSII masks** | `AF17_v11.gds`, `BF49.gds`, `GF97.gds` | Commit while they are byte-reproducible and within the size rules below. They are the authoritative layout, and `SOURCE_DATE_EPOCH` makes them reproducible. |
| **D. Renderings** | `*_layout.svg`, `*_layout.png`, `docs/af17-*.svg` | Previews of C. Commit only when small (1 MiB limit). Anything larger is a release asset, regenerated with `tools/gds_preview.py`. |
| **E. Calibration cache** | `results/cz_cache.json` | Commit. Keyed by CZ model version and every numerical setting; a stale cache is rejected, not trusted. Regenerate only on a `CZModel::kVersion` bump. |
| **F. Frozen history** | `results/alpha1_review.*` (Alpha-1 v1.0) | Commit, marked historical in `results/PROVENANCE.md`; not regenerated and not covered by the reproducibility check. |

Not committed: anything under a build directory, smoke-run output, scratch `--out` directories, logs with machine paths.
Do not delete committed outputs in a clean-up PR; shrink or move them through the process in section 4.

## 2. When to regenerate

Regenerate (class A, B, C, D, and E where it applies) in the **same PR** when a change touches anything on the path from input to output:

- numerics: `include/`, `src/`, `examples/`, the build flags in `CMakeLists.txt` (for example `-ffp-contract=off`), `CZModel::kVersion`;
- inputs: a design preset or design JSON, `layout_cells.json`, a seed, a shot count;
- the generator itself (`tools/fill_spec.py`, a template).

Do not regenerate for documentation, CI or test-only changes, and not merely to refresh a timestamp: if a GDS file's geometry
matches a rerun of its documented command, keep the committed file (as PR #23 did for `AF17_v11.gds`).

How: from a **clean checkout** (the review JSON must say `source_tree_dirty: false`), using the Release build and the exact command in
`results/PROVENANCE.md`. Never hand-edit a generated file, and never append a note to one: put the explanation in
`PROVENANCE.md` or the PR.

## 3. Provenance and seed metadata

- Every generated output has a row in `results/PROVENANCE.md`: program and arguments, source commit, compiler, OpenMP threads (informational), finish time (UTC), runtime. `check_reproducibility.py policy` fails if an output listed in `tools/results_policy.json` has no row.
- Every review JSON carries a `provenance` block: `source_commit`, `source_tree_dirty`, `compiler`, `openmp_threads`, `date_utc`, `seeds`, `cz_model_version`, `cz_cache`, `arguments`, `smoke`. A seed lives in the program, is recorded under `provenance.seeds` and in `PROVENANCE.md`, and changing one is a regeneration PR.
- Since 0.4 the Monte Carlo is **independent of the thread count** (`docs/design/deterministic-mc.md`) and the build is independent of the FMA setting, so a rerun reproduces every number at any `OMP_NUM_THREADS` and with g++ or clang.
- **Measured, not computed** (the only fields allowed to differ between two runs): `runtime_s`, `date_utc`, `decode_us_per_round*` and the decode times printed in the text, the `provenance` block apart from `seeds` and `cz_model_version`, and the BGNLIB/BGNSTR dates in a GDS file (pinned with `SOURCE_DATE_EPOCH`). Everything else must match byte for byte. `results/test_output.txt` contains timings and is not diffed; `ctest` and its check count cover it.
- GDS files are written with `SOURCE_DATE_EPOCH` set to the date already in the committed file, so a regeneration that changes nothing changes no bytes.
- A release asset (section 4) is listed in `PROVENANCE.md` with its name, size, SHA-256 and the command that produced it.

## 4. Size limits

| limit | value | enforced by |
|---|---|---|
| any tracked file under `results/`, `designs/`, `docs/` | **1 MiB** | `check_reproducibility.py policy`, every push and PR |
| the same files in total | **48 MiB** (44.5 MiB at `0629252`) | same |
| a class C file above 1 MiB | allowed only if it is regenerated by the check (the `gds` list in `tools/results_policy.json`, or a review program in the full tier) and is at most **10 MiB** | review |
| anything above 10 MiB | not committed: a **release asset** with its SHA-256 in `PROVENANCE.md` | review |
| files already above the limit | **grandfathered at their current size** in `results_policy.json` and may not grow. Shrinking one is free; regenerating a larger one means editing that file in the same PR, so the reviewer sees it | policy check |

Today ten files are grandfathered, at their sizes on `main` at `0629252` (the merge of #19): `GF97_layout.svg` (14.6 MB), `BF49_layout.svg` (7.3 MB),
`GF97.gds` (5.4 MB), `BF49.gds` (2.7 MB), five AF-17 SVGs (2.6 to 2.7 MB each: `AF17_v11_layout.svg`, `AF17_v11_detail.svg` and the three under
`docs/from-committed-layout/`) and `AF17_v11.gds` (0.96 MB, under the limit but pinned). **#19 grew them:** its regenerated previews took
`AF17_v11_detail.svg` from 168 KB to 2.7 MB, `af17-q5.svg` from 152 KB to 2.7 MB and `af17-zoom.svg` from 374 KB to 2.6 MB, and the governed total from
37.7 to 44.5 MiB, which is why the limits here were re-based on `0629252` and not on the earlier `main`. `GF97_layout.svg` is above the 10 MiB cap and is
the first candidate to become a release asset (it is a rendering, class D). Nothing is deleted by this PR.

**Git LFS is not used.** Merging through the GitHub UI, forks and CI checkouts all need LFS support and quota, and the GDS files are small
enough to stay in Git. Release assets (attached to the tag, with a hash in `PROVENANCE.md`) cover what is too big.

## 5. Review rules

A PR that changes a governed file:

1. says which class (section 1) each changed file is and links the `PROVENANCE.md` rows it updated;
2. passes the **Reproducibility** check, which regenerates the cheap deterministic outputs and diffs them bit-for-bit (section 7); for the review JSON, the full tier must also be green on `main` before the next tag;
3. for a numeric change, includes a **claim-changes table** (old value, new value, source file) like the one in PR #23, so a reviewer reads the effect, not the diff; a change that reverses a stated conclusion says so in the title;
4. is not accepted with `source_tree_dirty: true`, with a hand-edited generated file, or with a regenerated file whose only change is a timestamp;
5. for a GDS or SVG change, is reviewed through `tools/check_reproducibility.py compare <checkout-A> <checkout-B>` (hashes after masking) and a rendering, not by reading binary diffs;
6. never grows a grandfathered file or adds one over 1 MiB without editing `tools/results_policy.json` and saying why in the PR.

The reviewer's questions are: is every changed number explained by a code or input change in the same PR, and does the check pass?

## 7. The check

`python3 tools/check_reproducibility.py <policy|regen|compare>`; see its docstring. CI (`.github/workflows/reproducibility.yml`):

| tier | when | what | cost |
|---|---|---|---|
| **policy + fast** | every push and pull request, g++ and clang | size limits and provenance coverage; regenerate `results/design_study.{csv,txt}` (300 trajectories), `AF17_v11.gds` from `alpha1_v11.json` and `layout_cells.json`, and the Beta-1 and Gamma-1 specs from their review JSON; byte-compare each | ~2 min in CI on `5495bce` (98 s gcc / 125 s clang, run 46103746519); re-measured on this branch, because #19 grew AF-17 |
| **full** | nightly and manual only, like `smoke` in `ci.yml` | rerun `alpha1_v11_review`, `beta1_review`, `gamma1_review` at 100000 shots (about 42 minutes at 4 threads in the committed runs: 399 s, 1141 s, 982 s) and compare their JSON, text, `alpha1_v11.json`/`beta1.json`/`gamma1.json` and `BF49.gds`/`GF97.gds`; run `surgery_study --smoke` (d = 3, strips 1 and 3, 200 shots) and compare, for every point it shares with `results/surgery_study.json`, the fields the shot count does not change (noiseless checks, circuit, schedule, detector error model, seeds) | ~42 min at 4 threads (399 + 1141 + 982 s committed at `0629252`); the 5495bce mirror 46103766049 took ~45 min and failed on unmasked `--out` paths (fixed here) |

The full-tier check masks `runtime_s` / `date_utc` / decode times, GDS date fields, and — in this branch — any `-> path`, because `--out DIR` rewrites those paths. PR #20's `decoder_study` / `decoder_sweeps` outputs are not in the regen lists yet. `results/surgery_study.{json,txt}` are listed as generated outputs, but the committed 100000-shot run takes over an hour, so the full tier checks it only through the smoke comparison above: the logical errors and decode times of the committed file are checked by nothing but a rerun of the command in `results/PROVENANCE.md`.

Why this split: a review program run is 7 to 19 minutes and the three together are about 42, which is far too slow for every PR, and the
committed shot counts are the point of the check, so a reduced run proves nothing about the committed files. What a PR can afford is the
part of the output set that is cheap and still catches the real failure modes: a change to the Monte Carlo or the trajectory emulator (`design_study`
moves), to the GDS writer or cell assembly (`AF17_v11.gds` moves), to a template or `fill_spec.py` (the specs move), and a file that grew past its
limit. A change that only affects the review programs is caught nightly, and before a tag by running the `full` job (`workflow_dispatch`). The
nightly job is gated the same way `smoke` is, because it needs a runner for over half an hour and the committed cache.

Run locally: `cmake --build build --target design_study qpuforge_cli && python3 tools/check_reproducibility.py regen --tier fast --build build`.
